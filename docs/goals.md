# Spine Framework Goals

High-level objectives that guide framework design and determine what belongs in the shared core versus domain-specific layers.

## Primary Goal

Provide a foundation for building domain-specific authoring tools where:
- Content is primarily generated by LLMs
- Validation and analysis are performed by LLMs
- Internal consistency, cross-references, and constraints are enforced automatically
- Human authors review and approve rather than write from scratch

## LLM Architecture

Spine uses LLMs at multiple isolated levels:

### Level 1: Content Generation (Internal)

LLMs generate the actual content within the system:
- **Serial**: Outlines, beat sheets, prose drafts, chapter content
- **TechBook**: Explanatory prose, code comments, concept definitions

This is managed by domain core packages and uses context assembly to provide relevant information to the LLM.

### Level 2: Validation & Analysis (Internal)

LLMs perform quality checks and analysis:
- **Serial**: Continuity checking, tension scoring, voice consistency, pacing assessment, hook strength
- **TechBook**: Explanation clarity, coverage assessment, concept dependency validation

These are "computed" validators in the validation pipeline—expensive but capable of subjective judgment.

### Level 3: Interface (External)

The MCP and CLI provide the control interface:
- Can be driven by humans directly
- Can be driven by LLMs (e.g., Claude via MCP)
- Agnostic to who/what is issuing commands
- Orchestrates the internal LLM operations

**Key separation**: The LLM driving the interface (Level 3) is isolated from the LLMs doing content generation and validation (Levels 1-2). They may be different models, have different contexts, and serve different purposes.

### Why This Matters

- **Context isolation**: Interface context ≠ generation context ≠ validation context
- **Model flexibility**: Different levels can use different models (fast for validation, capable for generation)
- **Auditability**: Human can review what the generation LLM produced without needing to understand how the interface LLM orchestrated it
- **Token efficiency**: Each level assembles only the context it needs

## Target Domains

### Web Serials (Serial Domain)

Long-form serialized fiction with:
- Story bible tracking (characters, locations, factions, world rules, plot threads)
- Continuity enforcement across chapters
- Pacing analysis and tension curve management
- Release buffer and scheduling

Content evolves linearly; published content is immutable.

### Technical Books (TechBook Domain)

Progressive-build books where:
- Working code is tangled (extracted) from prose
- Checkpoints must compile and pass tests
- Concepts are tracked with prerequisite ordering
- Pedagogical order differs from file order

The book is the source; generated code is an artifact.

These two domains validate the framework. If both can be built cleanly on shared infrastructure, the framework succeeds.

## Core Objectives

### 1. LLM-Powered Content Pipeline

The system assumes LLM generation as the primary content source:
- Context assembly optimizes what the LLM sees for each task
- Token budgeting ensures efficient use of context windows
- Generation pipelines break complex tasks into manageable stages
- Self-review passes catch obvious issues before human review

### 2. LLM-Powered Validation

Subjective quality judgments use LLM analysis:
- Validators explain their reasoning (not black-box scores)
- Computed validation phase runs after cheaper structural/automated checks
- Analysis results are stored for review and trending
- Confidence scores indicate certainty of judgments

### 3. Structural Consistency

The framework provides primitives for tracking entities, references, and constraints:
- Entities have identity, properties, lifecycle, and relationships
- Content references entities; references are extracted and indexed automatically
- Constraints are declared, checked, and reported uniformly
- Cross-references are resolved for both validation and rendering

### 4. Validation Pipeline

All domains need to check constraints. The framework orchestrates; domains provide validators:
- **Structural** (fast): Graph queries, reference resolution, schema validation
- **Automated** (external tools): Compilers, test runners, linters
- **Computed** (LLM): Subjective analysis, consistency checks, quality scoring

### 5. Storage Consistency

All domains need persistent storage with similar characteristics:
- SQLite for indexes, entity registry, reference graph, validation results
- File system for authored content (diffable, editor-friendly)
- Derived data is rebuildable from source
- Single-project portability (one folder = one project)

### 6. Server Architecture

A WebSocket server provides a consistent API for all clients:
- JSON-RPC 2.0 protocol over WebSocket
- Framework provides server infrastructure and common operations
- Domains register handlers for domain-specific operations
- Single tested interface regardless of client type (human CLI, LLM MCP)

### 7. Extension Clarity

The boundary between framework and domain must be obvious:
- Clear extension points (spine shape, entity types, content types, validators)
- Base implementations for common patterns
- Type safety across the boundary
- Domains extend, never fork

## Non-Goals

### Not a Web Application

Spine is CLI and MCP only. No bundled web frontend. The WebSocket server enables future web clients but shipping one is not a framework goal.

### Not Human-First Authoring

While humans can write content directly, the system is optimized for LLM generation with human review. Manual authoring is supported but not the primary workflow.

### Not a Collaborative Platform

Single-author tools. Real-time collaboration, conflict resolution, and multi-user permissions are out of scope. Version control is external (git).

### Not a Runtime

Spine produces artifacts (manuscripts, tangled code, exported content). It does not run interactive fiction or serve documentation. Export to platforms is a feature; being a platform is not.

### Not Infinitely Flexible

The framework encodes opinions about how structured authoring works. Domains that don't fit the spine/entity/content/constraint model should use different tools.

## Success Metrics

1. **Generation acceptance rate**: >80% of LLM-generated content approved with minor or no edits
2. **Validation accuracy**: LLM validators catch >90% of issues that humans would flag
3. **Extraction ratio**: >60% of code in a domain tool comes from the framework
4. **Second-domain velocity**: Building the techbook domain takes <50% of the time the serial domain took
5. **Context efficiency**: Generation uses <50% of available context window on average

## Framework Principles

### Extract, Don't Speculate

The serial domain exists. Extract the framework from working code. Abstractions discovered in practice are better than abstractions designed in theory.

### Composition Over Inheritance

Domains compose framework pieces; they don't inherit from deep hierarchies. Extension points are interfaces and registries, not base classes.

### Explicit Extension Points

Every place where domains plug in is documented and typed. No "override this protected method" patterns. If it's not an explicit extension point, domains can't depend on it.

### Domain Logic Stays in Domains

The framework doesn't know what a "character" or "snippet" or "checkpoint" is. It knows about entities, content, and constraints. Domains define their specific types and behaviors.

### Validation is Not Optional

Every domain must have validators. The framework makes validation easy to implement and impossible to skip. A domain with no constraints isn't using Spine correctly.

### LLM Context is Precious

Context assembly is a first-class concern. Every token sent to an LLM should earn its place. Relevance scoring, summarization, and token budgeting are framework features.

### Human Authority Over LLM Output

LLMs generate and analyze; humans approve. No content reaches "published" status without explicit human action. The system suggests, the human decides.

## Glossary

**Spine**: The structural backbone of a project. Determines ordering, hierarchy, and checkpoint boundaries. Domain-specific in shape, common in interface.

**Entity**: A thing that exists in the project world. Has identity, properties, lifecycle, and relationships. Domain defines entity types; framework provides registry and graph.

**Content**: Authored material. Hangs from spine nodes, references entities. Domain defines content types; framework provides storage and reference extraction.

**Constraint**: A rule that must hold. Checked by validators, reported uniformly. Can be structural (graph properties), automated (external tools), or computed (LLM).

**Validator**: Checks constraints, produces results. Domains provide validators; framework orchestrates execution and aggregates results.

**Reference**: A link from content to an entity. Extracted automatically, indexed for queries, resolved during rendering.

**Checkpoint**: A named point in the spine where validation occurs and snapshots are taken. Domain determines checkpoint semantics.

**Domain**: A specific authoring use case (web serial, technical book, etc.) built on the framework. Provides entity types, content types, validators, and CLI/MCP tools.

**Context Assembly**: The process of selecting and formatting information for LLM consumption. Includes relevance scoring, token budgeting, and summarization.

**Generation Pipeline**: A sequence of LLM calls that produce content, typically with increasing detail (outline → beats → draft).

**Computed Validation**: Validation performed by LLM analysis rather than deterministic checks. Used for subjective quality judgments.
